# 文書の構造 — 木・構造の規則・cite

issue: #109

## 何のためか

契約書・仕様書・マニュアル・本のような**構造のある文章**を、番地の付いた木として扱う。
木があれば、機械で確かめられることが増える。存在しない条を指している、番号が飛んでいる、
同じ語が二通りに定義されている、回答が引いた箇所が原文に無い。どれも文章のコンパイルエラーである。

chaff は機械判定に徹する。木を読んで書き換える・答えるのは Claude Code 側（設計図のパック）で、
chaff はその前後で「壊れていないか」を判定する。linter と単体テストの役である。

## 決めたこと

- **木は本体が作り、言語ごとの型は言語パッケージが持つ。** 本体は「第3条」も「Article 3」も知らない。
  言語パッケージが番号の型・定義の言い回し・参照の型・義務の語・数の読み方を渡し、本体はそれを当てるだけ。
  これで、利用者が `lang-zh` を書けば中国語でも同じ木ができる。
- **言語パッケージの読み込みを開く。** いまは `ADAPTER_PACKAGE` に ja / en が書き込まれている（adapter-load.ts）。
  既定の対応は残し、無い言語は `@chaffjs/lang-<id>` を探し、`chaff.yaml` の `languages` で場所を指定もできる。
  言語の推定（detect.ts）は、読み込めた言語パッケージ全部の `detect` に聞く。
- **`.txt` も読む。** 契約書は Markdown でないことが多い。`.txt` は見出しを持たないので、番号の型だけで木を作る。
- **番地は正規化した番号の並び。** 第3条第2項第1号 → `3.2.1`、Section 4.2(a) → `4.2.a`。書かれたままの形は `label` に残す。
  番号の無い見出し（マニュアルの「インストール」など）は、見出しの並び順から `h2.3` のように振る。
- **出力は S 式と JSON。** S 式は人と AI が読むため、JSON は機械が読むため。同じ木から作る。
- **機械で確かめられないものは出さない。** 「矛盾しているか」の判断は AI 側。chaff が出すのは、
  参照先が無い・番号が抜けている・同じ語に食い違う定義がある、のように**書いてあることだけで決まる**もの。
- **新しい規則はすべて `status: experimental`** から始める。

## 木の形

```lisp
(doc "contract.txt" :language "ja"
  (article "3" :label "第3条" :heading "支払" :line 12
    (item "3.1" :label "第1項" :line 13
      (definition :term "本件代金" :line 13)
      (obligation :marker "しなければならない" :line 13)
      (quantity :value 30 :unit "日" :line 13)
      (ref :target "12" :label "第12条" :line 13))))
```

節（`section`）・番号付きのまとまり（`article`・`item`）が入れ子を作る。定義・参照・義務・数量は、
それが現れた最も内側のまとまりの子になる。すべての節点が `span`（UTF-16 の位置）と `line` を持つ。

## 契約の変更（`plugin.ts`）

adapter に任意の `structure` を足す。任意なので `apiVersion` は 1 のまま。

- `NumberedLine`: 行頭の番号 1 つ。`kind`（article / item）、`depth`、`number`（番地の部品）、`absolute`（それだけで番地が決まるか）、`label`（書かれたまま）、`heading`（見出し）、`rest`（番号の後ろ全部。定義や参照はここから探す）。
- `NumberingContext`: 開いている番号の並びと、Markdown の見出しの行か。「(i)」の読み分けと、本文の「1. 」を箇条書きのままにするために要る。
- `StructurePatterns`: `numbered`・`definitions`・`references`・`obligations`・`quantities` の 5 つの関数。正規表現の組ではなく関数にしたのは、漢数字やローマ数字の読み方、周りを見た読み分けを adapter が持てるようにするため。
- `StructureNode`: `kind`・`address`・`span`・`line`・`attrs`・`children`。見出しや書かれたままの番号は `attrs` に入れる。

正規表現はどれも後戻りの爆発を起こさない形に限る。数と単位は 1 つの正規表現に詰めず、数を見つけてから直後の単位を見る。

## 段階（PR を分ける）

1. **木**: 型・言語パッケージの型（ja / en）・木を作る処理・`chaff tree`・`.txt`・言語パッケージの読み込みを開く。
1b. **形態素・章・日付**: 日本語の数量を助数詞の品詞で読む、編・章・節と PART・CHAPTER、日付の葉、
   「1.5 倍」を通し番号にしない `countedAfter`、日英の見本と人が確かめた期待の木。
2. **構造の規則**: `dangling-reference`、`numbering-gap`、`duplicate-definition`（「食い違う」かは機械で決まらないので、名前は二重定義にした）。
   機械向けの出力は既存の SARIF（`--sarif`）で足りるので、指摘の JSON 出力は足さない。
2b. **巨大な文書**: 何万行の契約書で、lint が行数に対して二乗に遅くなる（前からある）。原因は二つ。
   - `placeOf`（指摘の位置 → 行番号）が指摘ごとに全行をなめていた。二分探索にした。前の実装と生成した入力で比べて差が無いことを確かめ、性質を恒久の試験に残した。
   - 文の分割に使う sentence-splitter が、文を閉じるたびに「それまでに閉じた括弧の組」をすべて並べ替えて文に付ける（`close()` の `consumedContexts`）。
     括弧の多い契約書が一つの段落（空行の無い .txt）で来ると、文の数 × 括弧の数に比例する。最新の 5.0.1 でも同じ。
     **段落を区切って渡す回避は見送った**: 区切っても同じ文になる位置を決めるには、ライブラリの括弧と略語の規則を写す必要があり、
     写した規則で試すと前の実装と一割ほど文の切れ目が食い違った。直すなら上流（sentence-splitter）で、報告するかは人が決める。
3. **`chaff cite`**: 回答の引用（番地と引用文）が原文の木に実在し、引用文が一致するかを確かめる。
   spec §25 の「原文との対応は対象外」を改める。書き換えはしない（§25 のまま）。

## 確かめ方

- 日本語と英語のそれぞれで、木の形を丸ごと比べる試験（入れ子・番地・行）。誤検出しやすい例（本文中の「第3条」への言及と、条の見出しの区別など）を必ず対にする（spec §23）。
- 木は決定的であること。同じ入力から同じ S 式が出る。
- 言語パッケージを足すだけで動くことを、試験の中で作った最小の言語パッケージで確かめる。
- Windows を含む CI。改行 `\r\n` の試験を入れる。
