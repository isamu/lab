# AIっぽさを直す

生成された文章には、よく出る形があります。太字の多さ、「X ではありません。Y です」の対比、
「重要なのは、」で始まる文、コロンから箇条書きへ渡す節などです。
chaff はこの形を機械で見つけますが、文章は書き換えません。
このページでは、見つけた形を手がかりに、人の書いた文章に近づける手順を説明します。

## chaff が見る AI っぽさ

AI っぽさのルールの多くは試験中で、`--experimental` を付けると動きます。`bold-density`、`closing-cliche`、`padded-intro` は付けなくても動きます。

```bash
npx chaffjs article.md --experimental    # 試験中のルールも動かす
```

| ルール | 見つけるもの |
| --- | --- |
| `ai-tell` | 生成文に多い言い回しの重なり（「重要な役割を果たす」「静かに壊れる」「時間を溶かす」） |
| `contrast-framing` | 「単なる X ではなく Y」「X ではありません。Y です」の対比の枠の重なり |
| `stock-transition` | 「さらに、」「加えて、」で始まる文の密度 |
| `announcing-opener` | 「重要なのは、」「ポイントは、」「正直に言うと、」で始まる文の重なり |
| `colon-lead-in` | 「以下の通りです：」のように、コロンで箇条書きへ渡す文の密度 |
| `assistant-residue` | 「お役に立てれば幸いです」のような、チャットの返事の名残 |
| `closing-cliche` | 「いかがでしたでしょうか」で締める終わり方 |
| `bold-density` | 太字の多さ |
| `no-em-dash` | ダッシュ（——）の多さ |
| `sentence-rhythm` | 文の長さが揃いすぎている所 |
| `rule-of-three` | 箇条書きがどれも 3 項目の所 |
| `ai-generated-composite` | 次の特徴のうち 3 つ以上がそろった文書：`ai-tell`、`contrast-framing`、`stock-transition`、`announcing-opener`、`colon-lead-in`、`assistant-residue`、`closing-cliche`、`padded-intro`、`no-em-dash`、`sentence-rhythm`、`rule-of-three`、`section-length-uniformity`（`bold-density` は数えません） |

どのルールも、それだけで「AI が書いた」とは言いません。人も書く形です。
重なったときに、読み返す場所の目印になります。

## 3 つの直し方

| 直し方 | 直すもの | 向いているとき |
| --- | --- | --- |
| 部分直し | 指摘された所だけ | 中身も構成もよく、言い回しだけが気になるとき |
| 節ごとの書き直し | 節ごとの文章。見出しの構成は残します | 構成が決まっている文書（報告書の型、手順書、必須の節がある文書） |
| 全面書き直し | 文書の全体。構成から作り直します | 「全面的に」「一から」と頼まれたとき。ブログとエッセイ。`ai-generated-composite` が出たとき |

部分直しは、指摘を一つずつ消していく直し方です。誤字や長い文は直りますが、文書の形は残ります。
節ごとに書き直しても、見出しの構成は元のままです。
数段落ごとの見出し、太字の書き出し、本文を繰り返す「まとめ」は、文を直しても生成文に読めます。

ブログとエッセイでは、全面書き直しを勧めます。`ai-generated-composite` が出た文書も同じです。
書き手が変えたいのは、たいてい文ではなく構成だからです。

## 部分直しの手順

1. `npx chaffjs article.md --experimental` をかけ、AI っぽさのルールの指摘を集めます。
2. 指摘された所だけを書き直します。意味、数、条件、技術的な制約は残します。
3. もう一度 chaff をかけます。書き直しは 2 回までにします。
4. 書き直した文章と、何をなぜ変えたのかの短い一覧を残します。

警告を消すためだけに繰り返しません。言い換えた語がまた別のルールに当たっても、
文脈で正しい専門用語ならそのまま残します。

## 節ごとの書き直しの手順

節ごとの書き直しは、見出しの構成を残したまま、節ごとに文章の形を変えます。

1. 書き直す前に `--experimental` で chaff をかけ、文書全体の特徴を控えます。
   控えるのは、`ai-generated-composite` に入る特徴、`bold-density`、`contrast-framing`、
   `stock-transition`、`sentence-rhythm` です。
2. 節ごとに、次の形を減らしながら書き直します。

| 減らす形 | 書き直し方 |
| --- | --- |
| 太字 | 本当に読み飛ばされては困る語だけに残します |
| 一文だけの段落、短い決め台詞 | 前後の段落に戻し、理由と一緒に書きます |
| 「X ではありません。Y です」 | 誰も言っていない X を消し、Y だけを書きます |
| 箇条書きばかりの節 | 項目どうしの繋がりがあるなら、文に戻して繋がりを書きます |
| ダッシュ（——） | 読点か括弧にするか、文を分けます |
| 予告だけの文（「重要なのは、」） | 予告を消し、中身から書き始めます |

3. 段落には主張を一つ持たせ、接続の言葉で前の段落と繋ぎます。
   元の文章に書き手の経験や具体的な数があれば、それを段落の中心に置きます。
4. もう一度 `--experimental` で chaff をかけ、1 で控えた特徴と比べます。
   変わったことは、言葉ではなく chaff の結果で示します。
5. `npx chaffjs compare <書き直す前> <書き直した後>` をかけ、落ちた事実と足された事実を確かめます。
   数、日付、時刻、URL、コード、固有名詞、引用、見出し、条項の参照、脚注を、前と後で突き合わせます。
   落ちた事実は戻します。事実でないもの（比喩の中の数、消した節の見出し）は、戻さない理由を残します。
   わざと消した種類は `--allow-dropped <種類>` で外せます。

## 全面書き直しの手順

全面書き直しでは、元の文を直しません。元の文書が言っていることを控えに取り、そこから書き起こします。

1. 書く前に控えを取ります。`npx chaffjs facts <file> --json` で、`compare` が照合する事実の一覧を出します。
   `npx chaffjs outline <file>` で、元の構成と形を出します。
   書き手の主張と、具体的な経験・例・意見は、一行に一つずつ書き出します。書き直しは、元の文ではなくこの控えから書きます。
2. 構成を捨てます。誰が何のために読むのかを決め、文書全体の切り口や話の筋を一つ選びます。
   そのうえで、書き始める前に次の組み替えを済ませます。

| 組み替え | すること |
| --- | --- |
| 順番を変える | 結論か、いちばん面白い出来事を先に置きます |
| 節を合わせる・分ける | 薄い節は合わせ、詰め込みすぎた節は分けます。一段落ごとに見出しを立てません |
| 繰り返すだけの節を消す | 本文を言い直すだけの節は消します。最後の「まとめ」も同じです |
| 一段落だけの見出しを外す | 見出しの下に一段落しかなければ、見出しを外して前後に合わせます |
| 要点の箇条書きを話にする | 要点を並べただけの節は、一本の筋を持つ文章にします |
| 3 点の対称をやめる | 中身が本当に 3 つでない限り、3 つの節や 3 つの項目に揃えません |
| 経験を動かす | 書き手の具体的な経験は、主張を支える場所に置きます |
| 書き出しを変える | 決まり文句の前置きをやめ、要点か具体的な場面から始めます |

3. 新しい構成を先に見せます。元の構成（`chaff outline` の見出し）と新しい構成を並べ、新しい側には節ごとに何を書くかを一行添えます。
   書き手が、構成の変わり方をひと目で見て決められるようにするためです。確認せずに進めてよいと頼まれていれば、そのまま書きます。
4. 控えから、書き手の声で書きます。

| 書き方 | 中身 |
| --- | --- |
| 段落 | 主張を持たせ、接続の言葉で前の段落と繋ぎます。文の長さは揃えません |
| 動詞 | 比喩（「静かに壊れる」）をやめ、何が起きるのかを書きます |
| 経験と数 | 書き手の出来事と数は残し、どの記事にも書ける埋め草は消します |
| 太字と箇条書き | 太字は読み落とされては困る所だけにします。箇条書きは、本当に並べるもの・手順・コマンドだけにします |
| 避ける形 | 主張にぼかしを重ねない、これから言うことを予告しない、「X ではなく Y」にしない、ダッシュを使わない |
| 調子 | 書き手のほかの段落の文末（です・ます か だ・である）と、載せる場所（Zenn、社内の報告、メール）に合わせます |
| 足さないもの | 控えに無い事実、人、数、原因、結果は書きません |

5. 確かめます。

```bash
npx chaffjs new.md --experimental                       # AI っぽさの特徴を前と後で比べる
npx chaffjs outline old.md new.md                       # 見出しの数・節の平均・箇条書き・太字を前と後で並べる
npx chaffjs compare old.md new.md --allow-dropped heading   # 見出し以外の事実が落ちても足されてもいないか
```

   見出しは、わざと捨てた構成なので `--allow-dropped heading` で外します。ほかに落ちた事実は戻し、足された事実は消します。
   元の文書が繰り返していただけの事実（消した「まとめ」の中の数など）は、理由を書いて外してかまいません。
6. 次のどれもが成り立ったら止めます。全面書き直しは 2 回までにします。
   - `ai-generated-composite` が出ない
   - 密度のルール（`bold-density`、`contrast-framing`、`stock-transition`、`colon-lead-in`）が上限より下にある
   - `compare` が通るか、外したものすべてに理由が書いてある
7. 書き直した文章、何をなぜ変えたのかの短い一覧、前と後の特徴と形の表を見せます。表の数は chaff の出力から取ります。

## 機械では見つけられない形

次の形は、chaff が機械では見つけられません。どの直し方でも、読んで確かめます。

| 形 | 読んで確かめること |
| --- | --- |
| 決まり文句の書き出しと締め | 「本記事では〜解説します」「いかがでしたでしょうか」で始めたり終えたりしていないか |
| 分かりきった説明 | 読み手がみな知っていることを説明していないか |
| 同じ形の節 | どの節も同じ長さ、同じ組み立てになっていないか |
| 利点だけの列挙 | 良いことだけを並べ、代わりに払うものを書いていないか |
| 一次の情報が無い | 書き手が見たこと、測ったこと、やったことが一つも無いか |
| 一様な熱量 | どこも同じ調子で褒めていて、何が大事なのか分からないか |
| 重ねた丁寧さ | 敬語や前置きを重ねすぎていないか |
| 頼まれていない定義 | 誰も聞いていない言葉の定義を置いていないか |
| 文になった見出し | 見出しが標語のような一文になっていないか |
| 繰り返す「まとめ」 | 最後の節が本文を言い直しているだけになっていないか |

## どの直し方でも守ること

- 元の文章に無い事実、人、数、原因を足しません。
- 意味、数、条件、技術的な制約は変えません。
- 否定の対比より、言いたいことをそのまま書きます。
- 誰が何をするのかを書きます。
- 書き直しは 2 回までにします。警告を消すためだけに繰り返しません。

## ジャンルごとの勘所

| ジャンル | 勘所 |
| --- | --- |
| 技術記事（`blog/tech`） | 比喩の動詞（「静かに壊れる」「黙って無視される」）は、何が起きるのかに言い換えます。「例外を出さずに処理を続ける」のように書きます。手順やコマンドの一覧は箇条書きのままにします。 |
| ビジネス文書（`business/report`） | 結論と、誰がいつ何をするのかを先に書きます。「単なるツールの導入にとどまらず」のような飾りを消します。表と数字はそのまま残します。 |
| エッセイ（`blog/essay`） | 一文だけの段落と決め台詞を前後に戻します。「真理」「新たな可能性」のような大きな言葉を、その場面で起きたことに置き換えます。 |

## 例：技術記事を節ごとに書き直す

生成文の書きぶりで書いた技術記事を、節ごとの書き直しで直した例です。
どちらの文書も、このページのために書いたものです。

書き直す前の記事です。

```markdown
# CI のテストがたまに落ちる問題を解決した話——時差という見えない罠

本記事では、CI でだけテストが不安定になる問題について、原因の特定から修正までを詳しく解説していきます。

## 何が起きていたのか

社内の在庫管理 API のテストが、CI でだけ**約 30 回に 1 回**落ちていました。手元では再現しません。

これは単なる不安定なテストではありません。**チームの時間を静かに奪う問題**です。

正直に言うと、私たちは三週間この問題を放置していました。再実行すれば通るからです。

しかし、再実行は 1 回 12 分。これが地味に効いてきます。気づけば時間を溶かしていました。

## 原因の調査

ポイントは、落ちた回のログを並べることです。

調査で分かったことは次の通りです：

- 落ちた回は**すべて日本時間の 0 時〜9 時**に実行されていた
- CI のランナーは **UTC** で動いている
- テストは `new Date()` で今日の日付を取り、期日を「今日から 7 日後」として計算していた

つまり、日本時間では月曜でも、ランナーの上ではまだ日曜だったのです。

重要なのは、エラーが黙って無視されていたことです。日付のずれは例外を出さず、テストは静かに壊れていました。

## 解決策

修正は以下の 3 つです：

- **テスト**：`jest.useFakeTimers` と `setSystemTime` で時刻を固定
- **ワークフロー**：`TZ=Asia/Tokyo` を追加
- **本番コード**：`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を渡して日付の境目を決定

さらに、本番コードまで直したことが鍵となります。テストだけでなく、本番のサーバーが UTC で動いた場合にも備える必要があるからです。

## 結果

修正後の二週間、このテストは**一度も**落ちていません。

## まとめ

時刻に依存するテストは、単なるバグではなく、環境そのものの問題です。不安定なテストを一つずつ潰していくことが、チームの生産性を大きく向上させる鍵となるでしょう。

いかがでしたでしょうか。この記事が皆さんのお役に立てれば幸いです。
```

```markdown
# CI のテストがたまに落ちる問題は時差が原因だった

社内の在庫管理 API のテストが、CI でだけ約 30 回に 1 回落ちていました。手元では再現しません。この記事では、原因を突き止めて直すまでを書きます。

## 何が起きていたのか

三週間ほど、私たちはこの問題を放っておきました。再実行すれば通ったからです。ただ、再実行には 1 回 12 分かかり、その待ち時間が積み重なっていきました。

## 原因の調査

落ちた回のログを並べると、すべて日本時間の 0 時から 9 時に実行されていました。CI のランナーは UTC で動いています。テストは `new Date()` で今日の日付を取り、期日を「今日から 7 日後」として計算していたので、日本時間では月曜でも、ランナーの上ではまだ日曜でした。

日付がずれても例外は出ないので、エラーとして表に出ることはありませんでした。

直したことは 3 つあります。テストでは `jest.useFakeTimers` と `setSystemTime` で時刻を固定し、ワークフローには `TZ=Asia/Tokyo` を足しました。本番のコードも、`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を渡して日付の境目を決めるように変えています。テストだけ直しても、本番のサーバーが UTC で動けば同じずれが起きるからです。

## 結果

直してからの二週間、このテストは一度も落ちていません。時刻に触るテストは、走る時間と場所で結果が変わります。たまに落ちるテストを見つけたら、まず落ちた時刻を並べてみてください。
```


最初にかけたときは、「修正は以下の 3 つです」の「3 つ」も落ちていました。
書き直しで箇条書きを文に戻したときに、数を言う文が消えていたためです。
「直したことは 3 つあります。」を足して戻し、もう一度かけた結果が上のものです。
残った 2 件は、事実ではないので戻していません。

| 落ちた事実 | 戻さなかった理由 |
| --- | --- |
| 見出し「まとめ」 | 締めの決まり文句と一緒に、節ごと消しました |
| 数「一つ」 | 「一つずつ潰していく」という比喩の一部で、数ではありません |

この書き直しでは、見出しの構成はほとんど動いていません。`npx chaffjs outline ai.md rewritten.md` で測ると、見出しは 6 から 5 に減っただけです。
構成から変えたいときは、次の例のように全面書き直しを選びます。

## 例：ブログ記事を全面的に書き直す

生成文の書きぶりで書いたブログ記事を、全面書き直しで直した例です。
どちらの文書も、このページのために書いたものです。

書き直す前の記事です。

```markdown
# 社内勉強会を半年続けて見えてきた、本当に大切なこと——継続の秘訣とは

本記事では、私たちのチームが半年間続けてきた社内勉強会について、その取り組みと学びを詳しく解説していきます。

## はじめに

エンジニアにとって、学び続けることは非常に重要です。技術の進化は速く、昨日の常識が今日には古くなっています。

そこで私たちは、2025年10月に社内勉強会を始めました。

## 勉強会の概要

勉強会の概要は以下の通りです：

- **頻度**：毎週木曜日 17:00〜17:30
- **参加者**：開発チームの 12 人
- **形式**：1 人が 15 分話し、残りの時間で質疑

## 直面した課題

### 参加者が減った

始めて 2 か月で、参加者は 5 人に減りました。これは単なる忙しさの問題ではありません。**勉強会の価値が伝わっていない**という問題です。

### 話す人が偏った

最初の 8 回のうち 6 回は、同じ 2 人が発表していました。

### 内容が業務と離れていた

取り上げた題材の多くは、Rust や新しいフレームワークなど、日々の業務では使わない技術でした。

## 実施した改善策

ポイントは、続けられる形に作り替えることです。改善策は次の通りです：

### 題材を業務から選ぶ

**発表の題材を、その週に詰まったことに限定しました。** たとえば、本番で起きた障害の振り返りや、レビューで指摘が多かった書き方です。

### 発表を短くする

**発表を 5 分に縮めました。** 準備の負担が減り、発表した人は半年で 9 人になりました。

### 記録を残す

**発表の内容を Notion に残すようにしました。** 欠席した人も後から読めます。

## 結果

さらに、これらの改善によって、参加者は 11 人に戻りました。重要なのは、数字だけではありません。チームの雰囲気そのものが変わったことです。

正直に言うと、ここまで効果が出るとは思っていませんでした。

## 学んだこと

学んだことは以下の通りです：

- **継続には仕組みが必要**：意志だけでは続きません
- **小さく始めることが鍵**：短い発表なら誰でも話せます
- **業務とのつながりが大切**：役に立つと分かれば人は集まります

## まとめ

本記事では、社内勉強会を半年続けた経験から、継続のためのポイントを紹介しました。継続には仕組みが必要であり、小さく始めることが鍵であり、業務とのつながりが大切です。勉強会は単なる学びの場ではなく、チームの成長において重要な役割を果たす場なのです。

いかがでしたでしょうか。この記事が、皆さんのチームで勉強会を始めるきっかけになれば幸いです。
```

```markdown
2025年10月に、開発チームで社内勉強会を始めました。毎週木曜日の 17:00 から 17:30 まで、1 人が 15 分話して、残りの時間で質疑をする形です。チームの 12 人で始めましたが、2 か月たつと、来るのは 5 人になっていました。

## 人が減ったのは、話が遠かったから

振り返ると、まず話す人が決まっていました。最初の 8 回のうち 6 回は、同じ 2 人が発表しています。題材も、Rust や新しいフレームワークのように、ふだんの業務では使わない技術が多くを占めていました。聞く側にとっては、面白くても明日の仕事には関わらない話です。忙しい週に足が遠のくのは、無理もありませんでした。

## その週に詰まったことを、短く話す

そこで、題材をその週に詰まったことに限りました。本番で起きた障害の振り返りや、レビューで何度も指摘された書き方です。どれも誰かが実際に困った話で、聞けば次の週の仕事に役立ちます。

参加者は 11 人まで戻りました。ここまで変わるとは思っていませんでした。

続かなかった原因は、意志の弱さより、話す側の準備の重さと、聞く側から見た題材の遠さにありました。どちらも仕組みで軽くできます。
```
