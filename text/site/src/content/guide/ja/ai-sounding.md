# AIっぽさを直す

生成された文章には、よく出る形があります。太字の多さ、「X ではありません。Y です」の対比、
「重要なのは、」で始まる文、コロンから箇条書きへ渡す節などです。
chaff はこの形を機械で見つけますが、文章は書き換えません。
このページでは、見つけた形を手がかりに、人の書いた文章に近づける手順を説明します。

## chaff が見る AI っぽさ

AI っぽさのルールの多くは試験中で、`--experimental` を付けると動きます。`bold-density`、`closing-cliche`、`padded-intro` は付けなくても動きます。

```bash
npx chaffjs article.md --experimental    # 試験中のルールも動かす
```

| ルール | 見つけるもの |
| --- | --- |
| `ai-tell` | 生成文に多い言い回しの重なり（「重要な役割を果たす」「静かに壊れる」「時間を溶かす」） |
| `contrast-framing` | 「単なる X ではなく Y」「X ではありません。Y です」の対比の枠の重なり |
| `stock-transition` | 「さらに、」「加えて、」で始まる文の密度 |
| `announcing-opener` | 「重要なのは、」「ポイントは、」「正直に言うと、」で始まる文の重なり |
| `colon-lead-in` | 「以下の通りです：」のように、コロンで箇条書きへ渡す文の密度 |
| `assistant-residue` | 「お役に立てれば幸いです」のような、チャットの返事の名残 |
| `closing-cliche` | 「いかがでしたでしょうか」で締める終わり方 |
| `bold-density` | 太字の多さ |
| `no-em-dash` | ダッシュ（——）の多さ |
| `sentence-rhythm` | 文の長さが揃いすぎている所 |
| `rule-of-three` | 箇条書きがどれも 3 項目の所 |
| `ai-generated-composite` | 次の特徴のうち 3 つ以上がそろった文書：`ai-tell`、`contrast-framing`、`stock-transition`、`announcing-opener`、`colon-lead-in`、`assistant-residue`、`closing-cliche`、`padded-intro`、`no-em-dash`、`sentence-rhythm`、`rule-of-three`、`section-length-uniformity`（`bold-density` は数えません） |

どのルールも、それだけで「AI が書いた」とは言いません。人も書く形です。
重なったときに、読み返す場所の目印になります。

## 2 つの直し方

| 直し方 | 直すもの | 向いているとき |
| --- | --- | --- |
| 部分直し | 指摘された所だけ | 中身も構成もよく、言い回しだけが気になるとき |
| 書き直し | 節ごとに、文書の全体の形 | 部分直しをしても、まだ生成文に読めるとき |

部分直しは、指摘を一つずつ消していく直し方です。誤字や長い文は直りますが、文書の形は残ります。
太字の見出しと箇条書きが続く記事は、言い回しを直しても生成文に読めます。
そのときは書き直しを選びます。

## 部分直しの手順

1. `npx chaffjs article.md --experimental` をかけ、AI っぽさのルールの指摘を集めます。
2. 指摘された所だけを書き直します。意味、数、条件、技術的な制約は残します。
3. もう一度 chaff をかけます。書き直しは 2 回までにします。
4. 書き直した文章と、何をなぜ変えたのかの短い一覧を残します。

警告を消すためだけに繰り返しません。言い換えた語がまた別のルールに当たっても、
文脈で正しい専門用語ならそのまま残します。

## 書き直しの手順

書き直しは、指摘の一つ一つではなく、文書の全体の形を変えます。節ごとに進めます。

1. 書き直す前に `--experimental` で chaff をかけ、文書全体の特徴を控えます。
   控えるのは、`ai-generated-composite` に入る特徴、`bold-density`、`contrast-framing`、
   `stock-transition`、`sentence-rhythm` です。
2. 節ごとに、次の形を減らしながら書き直します。

| 減らす形 | 書き直し方 |
| --- | --- |
| 太字 | 本当に読み飛ばされては困る語だけに残します |
| 一文だけの段落、短い決め台詞 | 前後の段落に戻し、理由と一緒に書きます |
| 「X ではありません。Y です」 | 誰も言っていない X を消し、Y だけを書きます |
| 箇条書きばかりの節 | 項目どうしの繋がりがあるなら、文に戻して繋がりを書きます |
| ダッシュ（——） | 読点か括弧にするか、文を分けます |
| 予告だけの文（「重要なのは、」） | 予告を消し、中身から書き始めます |

3. 段落には主張を一つ持たせ、接続の言葉で前の段落と繋ぎます。
   元の文章に書き手の経験や具体的な数があれば、それを段落の中心に置きます。
4. もう一度 `--experimental` で chaff をかけ、1 で控えた特徴と比べます。
   変わったことは、言葉ではなく chaff の結果で示します。
5. `npx chaffjs compare <書き直す前> <書き直した後>` をかけ、落ちた事実と足された事実を確かめます。
   数、日付、時刻、URL、コード、固有名詞、引用、見出し、条項の参照、脚注を、前と後で突き合わせます。
   落ちた事実は戻します。事実でないもの（比喩の中の数、消した節の見出し）は、戻さない理由を残します。
   わざと消した種類は `--allow-dropped <種類>` で外せます。

## どちらでも守ること

- 元の文章に無い事実、人、数、原因を足しません。
- 意味、数、条件、技術的な制約は変えません。
- 否定の対比より、言いたいことをそのまま書きます。
- 誰が何をするのかを書きます。
- 書き直しは 2 回までにします。警告を消すためだけに繰り返しません。

## ジャンルごとの勘所

| ジャンル | 勘所 |
| --- | --- |
| 技術記事（`blog/tech`） | 比喩の動詞（「静かに壊れる」「黙って無視される」）は、何が起きるのかに言い換えます。「例外を出さずに処理を続ける」のように書きます。手順やコマンドの一覧は箇条書きのままにします。 |
| ビジネス文書（`business/report`） | 結論と、誰がいつ何をするのかを先に書きます。「単なるツールの導入にとどまらず」のような飾りを消します。表と数字はそのまま残します。 |
| エッセイ（`blog/essay`） | 一文だけの段落と決め台詞を前後に戻します。「真理」「新たな可能性」のような大きな言葉を、その場面で起きたことに置き換えます。 |

## 例：技術記事を書き直す

生成文の書きぶりで書いた技術記事を、書き直しで直した例です。
どちらの文書も、このページのために書いたものです。

書き直す前の記事です。

```markdown
# CI のテストがたまに落ちる問題を解決した話——時差という見えない罠

本記事では、CI でだけテストが不安定になる問題について、原因の特定から修正までを詳しく解説していきます。

## 何が起きていたのか

社内の在庫管理 API のテストが、CI でだけ**約 30 回に 1 回**落ちていました。手元では再現しません。

これは単なる不安定なテストではありません。**チームの時間を静かに奪う問題**です。

正直に言うと、私たちは三週間この問題を放置していました。再実行すれば通るからです。

しかし、再実行は 1 回 12 分。これが地味に効いてきます。気づけば時間を溶かしていました。

## 原因の調査

ポイントは、落ちた回のログを並べることです。

調査で分かったことは次の通りです：

- 落ちた回は**すべて日本時間の 0 時〜9 時**に実行されていた
- CI のランナーは **UTC** で動いている
- テストは `new Date()` で今日の日付を取り、期日を「今日から 7 日後」として計算していた

つまり、日本時間では月曜でも、ランナーの上ではまだ日曜だったのです。

重要なのは、エラーが黙って無視されていたことです。日付のずれは例外を出さず、テストは静かに壊れていました。

## 解決策

修正は以下の 3 つです：

- **テスト**：`jest.useFakeTimers` と `setSystemTime` で時刻を固定
- **ワークフロー**：`TZ=Asia/Tokyo` を追加
- **本番コード**：`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を渡して日付の境目を決定

さらに、本番コードまで直したことが鍵となります。テストだけでなく、本番のサーバーが UTC で動いた場合にも備える必要があるからです。

## 結果

修正後の二週間、このテストは**一度も**落ちていません。

## まとめ

時刻に依存するテストは、単なるバグではなく、環境そのものの問題です。不安定なテストを一つずつ潰していくことが、チームの生産性を大きく向上させる鍵となるでしょう。

いかがでしたでしょうか。この記事が皆さんのお役に立てれば幸いです。
```

書き直した後の記事です。

```markdown
# CI のテストがたまに落ちる問題は時差が原因だった

社内の在庫管理 API のテストが、CI でだけ約 30 回に 1 回落ちていました。手元では再現しません。この記事では、原因を突き止めて直すまでを書きます。

## 何が起きていたのか

三週間ほど、私たちはこの問題を放っておきました。再実行すれば通ったからです。ただ、再実行には 1 回 12 分かかり、その待ち時間が積み重なっていきました。

## 原因の調査

落ちた回のログを並べると、すべて日本時間の 0 時から 9 時に実行されていました。CI のランナーは UTC で動いています。テストは `new Date()` で今日の日付を取り、期日を「今日から 7 日後」として計算していたので、日本時間では月曜でも、ランナーの上ではまだ日曜でした。

日付がずれても例外は出ないので、エラーとして表に出ることはありませんでした。

## 直したこと

直したことは 3 つあります。テストでは `jest.useFakeTimers` と `setSystemTime` で時刻を固定し、ワークフローには `TZ=Asia/Tokyo` を足しました。本番のコードも、`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を渡して日付の境目を決めるように変えています。テストだけ直しても、本番のサーバーが UTC で動けば同じずれが起きるからです。

## 結果

直してからの二週間、このテストは一度も落ちていません。時刻に触るテストは、走る時間と場所で結果が変わります。たまに落ちるテストを見つけたら、まず落ちた時刻を並べてみてください。
```

書き直した後に chaff をかけた結果です。

```text

  1:28    info    節の長さのばらつきが 32% しかありません（35% 以上ほしい）
                  section-length-uniformity

指摘 1 件、動いていない rule 8 件
```

変えたことと、その理由です。

| 変えたこと | 理由 |
| --- | --- |
| 題の「——時差という見えない罠」を消し、原因を題にしました | 予告ではなく、分かったことを題にするためです |
| 「本記事では〜詳しく解説していきます」を、記事が書くことの一文にしました | 決まり文句の書き出しで、中身がありません |
| 太字をすべて外しました | 数と事実だけで伝わり、強調する語がありません |
| 「単なる不安定なテストではありません」の対比を消しました | 誰も言っていない X を打ち消していました |
| 「正直に言うと」「ポイントは」「重要なのは」を消しました | 予告をやめ、中身から書き始めるためです |
| 「地味に効いてきます」「時間を溶かしていました」を「待ち時間が積み重なっていきました」にしました | 比喩をやめ、起きたことを書くためです |
| 「黙って無視されていた」「静かに壊れていました」を「例外は出ない」と言い換えました | 何が起きたのかを書くためです |
| 2 つの箇条書きを文に戻しました | 原因は 3 つの事実の繋がりで、並べるだけでは繋がりが書けません |
| 「いかがでしたでしょうか」「お役に立てれば幸いです」を消しました | 締めの決まり文句です |

数（30 回に 1 回、三週間、12 分、二週間）、コマンド、設定の値はすべて残しています。
書き直した後に残った `section-length-uniformity` は、節の長さが揃っていることを言っています。
中身のある節を足すと事実を足すことになるので、そのままにしました。

最後に、事実が落ちていないかを `chaff compare` で確かめた結果です。

```text

  見出し: 解決策 → 直したこと  (29 行目 → 15 行目)

照合した事実 33 件 → 30 件: 数 12→11、日付 0→0、時刻 0→0、URL 0→0、コード 6→6、固有名詞 8→7、引用 1→1、見出し 6→5、条項の参照 0→0、脚注 0→0
落ちた事実 2 件、足された事実 0 件
```

最初にかけたときは、「修正は以下の 3 つです」の「3 つ」も落ちていました。
書き直しで箇条書きを文に戻したときに、数を言う文が消えていたためです。
「直したことは 3 つあります。」を足して戻し、もう一度かけた結果が上のものです。
残った 2 件は、事実ではないので戻していません。

| 落ちた事実 | 戻さなかった理由 |
| --- | --- |
| 見出し「まとめ」 | 締めの決まり文句と一緒に、節ごと消しました |
| 数「一つ」 | 「一つずつ潰していく」という比喩の一部で、数ではありません |
