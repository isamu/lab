# scoria の使い方

はじめて聞いた人向けの案内です。詳しい仕様は
[README.ja.md](../packages/scoria/README.ja.md) にあります。ここは通しの説明です。

## これは何か

scoria は TypeScript / JavaScript のリポジトリを読んで、**いまどういう状態か**を9つの数字と、
その根拠になった指摘で教えてくれる道具です。読みやすいか、足りていないものは何か、どこが崩れ始めているか。

速く書かれたコードのためのものです。LLM が書いたコード、あるいは急いでいた人間が書いたコードは、
決まった壊れ方をします。1つのファイルが2000行に育つ。エラーを直す代わりに黙らせる。
最初に書いたものを誰も覚えていないので同じものをもう一度書く。scoria が数えているのはそういうものです。

**物差しは scoria が持ってきます。** あなたの ESLint 設定を読んでそれに照らして採点する、
ということはしません。**全部のルールを切ったプロジェクトが満点になってしまう**からです。

## 動かしてみる

準備は要りません。どのリポジトリでも:

```bash
npx scoria
```

20秒ほどで、こう出ます。

```text
my-project  [vue · react · ts]  profile: library
17 files · 1095 sloc · 619 test sloc   config: detected

  Dimension            Score   Confidence
  ──────────────────────────────────────────────────────────────
  architecture             —   high   only 0% of this dimension could be measured
  correctness             95   high
  documentation          100   high   only 75% of this dimension could be measured
  integrity               80   high
  readability             90   high
  security                86   high
  test-coverage          100   high   only 30% of this dimension could be measured
  type-safety             86   high   only 50% of this dimension could be measured
  ui-consistency           —   high   only 0% of this dimension could be measured
  ──────────────────────────────────────────────────────────────
  Overall                 91   not comparable across repos (mean of 7)
```

これは実際の初回実行です。そして**面白いのは右側の列**です。

## 読み方

### `—` は「誰も見ていない」

ダッシュは0点ではありません。**その観点について何も測れなかった**ので、数字を置くことを拒否しています。
上の例だと `architecture` がダッシュなのは、依存パッケージが install されておらず、
import をたどる道具がたどるものを持たなかったからです。`ui-consistency` は、コンポーネントが1つも無いから。

これは見た目より大事な話です。以前のバージョンは**空のディレクトリを100点満点中90点**と採点していました。
「問題が見つからなかった」と「何も見ていない」が同じ数字になっていたからです。
その2つは違うもので、いまのレポートは違うものとして扱います。

### 「only N% could be measured」

同じ考えを1段下でやっています。`type-safety` は86ですが、そのあとに「半分しか測れていない」と書いてあります。
測れた半分は「型の付いていないファイルの割合」で、もう半分は TypeScript コンパイラを走らせる部分 —
こちらはプロジェクトが install されている必要があります。
**「見た半分の中での86」は、「86」とは違う主張です。**

### `Overall … (mean of 7)`

9つ並んでいて、点が付いたのは7つ。だから平均は7つぶんです。
**少数の平均を全体の平均に見せない**ために、いくつから出した平均かを書いています。

### Confidence（信頼度）

普通は `high` です。それより低いときは、**その観点が「黙らされたエラー」ごしに測られた**という意味です
（`as any`、`@ts-ignore`、`eslint-disable` が多い）。
その数字はコードの話であると同時に、黙らせ方の話でもあります。**点数より先に信頼度を見てください。**

## 何を読んでいるか

### ファイル

指定されたディレクトリの中を歩き、**その外には出ません**。途中で、名前を見て次を飛ばします。

```text
node_modules   .git   dist   lib   build   coverage   .next   out   .turbo   .output
```

それと、ドットで始まるディレクトリ全部。残ったものを4種類に仕分けます。

| 種類   | 何が入るか                                                                                  | 扱い           |
| ------ | ------------------------------------------------------------------------------------------- | -------------- |
| ソース | `.ts` `.tsx` `.mts` `.cts` `.js` `.jsx` `.mjs` `.cjs` と `.vue`                             | 採点の対象     |
| テスト | `test/ tests/ __tests__/ __mocks__/ e2e/ spec/` の下、または `*.test.*` `*.spec.*` `test_*` | 別枠で数える   |
| 設定   | `*.config.ts` `*.config.js` `eslint.config.*` `vite.config.*` など                          | どちらでもない |
| 生成物 | `*.d.ts` `*.min.js`                                                                         | どちらでもない |

それ以外 — Markdown、JSON、画像、CSS — はコードとして読みません。2MB を超えるファイルは飛ばします。

`.vue` はソースとしては `<script>` の中だけをコードとして扱います。
テンプレートとスタイルは別に読んでいて、それが効くのは UI の検査だけです
（テンプレートの中の色はそこで意味を持つので）。

### 設定ファイル

ルートにある次のファイルも探して読みます。**そのプロジェクトが自分に課しているもの**を見るためです。

```text
package.json   tsconfig.json   jsconfig.json   eslint.config.*   .eslintrc*
.prettierrc*   .gitignore   knip.json   vitest.config.ts   jest.config.js
```

それと `.github/workflows/*.yml`。モノレポのように、測っている場所より上にワークフローがある場合は、
4階層まで上に探しにいきます。

**読むことと、それで採点することは別です。** `tsconfig.json` は TypeScript コンパイラに渡します —
型チェックはそのプロジェクトの設定でやる以外にないからです。
他は違う問いのために読みます。**このプロジェクトはゲートを持っているか、CI はそれを回しているか。**
lint 設定も CI も無いリポジトリはその点で低くなります。設定の中身が何であったかとは関係なく。

### どの部分を、何のために見ているか

| 読むもの                                        | 問い                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| ソースファイル全部                              | ファイルの大きさ、重複、型の付いていない割合、黙らせたエラーの数   |
| 同じファイルのコメント部分だけ                  | 置き去りの印: TODO、FIXME、XXX、HACK                               |
| `.vue` `.tsx` `.jsx` の全体                     | 色と余白の種類数、インラインスタイル、style ブロック               |
| テストファイル                                  | テストコードの量。それが対象とするコードとの比                     |
| `tsconfig.json` と install された TypeScript    | 型エラー                                                           |
| lockfile とパッケージマネージャ                 | 既知の脆弱性                                                       |
| import の依存グラフ                             | 誰も辿り着かないファイルと export、循環参照                        |
| `README.md`                                     | あるか、どれだけ書いてあるか、コードが受け取るフラグが載っているか |
| 設定ファイルとワークフロー                      | プロジェクト自身のゲートがあるか、CI がそれを回しているか          |
| `coverage/lcov.info` か `coverage-summary.json` | カバレッジ（すでにレポートがある場合だけ）                         |

## 全部を測れる状態にする

さっきの初回実行は9つ中7つでした。2つのコマンドで変わります。

```bash
npm install              # yarn でも。tsc・knip・循環参照の検出が動くようになる
npm test -- --coverage   # プロジェクトのカバレッジ用コマンド
npx scoria
```

**scoria はあなたのテストを実行しません。** テストは数分かかることも、DB に触ることも、
認証情報が要ることもあります。点数を聞かれただけでそれを全部引き起こす道具は、二度と使ってもらえません。
プロジェクトが**すでに作った**カバレッジレポート（`coverage/lcov.info` か
`coverage/coverage-summary.json`）を読むだけで、無ければ「読まなかった」と書きます。

## 変化を追う

点数が1つあっても、分かることは多くありません。大事なのは**向き**です。

```bash
npx scoria baseline       # いまの結果を記録する
git add .scoria/baseline.json
```

以降、実行するたびに「何が動いたか」が出ます。

```text
動いたもの
    -30.0  integrity      suppression-scan.source_per_kloc   0 → 975
    -20.0  integrity      suppression-scan.unreasoned_ratio  0 → 1
```

どの指標がどれだけ動いて、それが何点ぶんだったかを名指しします。
lint を更新するとルールが増えて点が下がりますが、**それは劣化ではありません**。
baseline にツールの版数も記録してあるので、そのときはそう言います。

## CI に入れる

```yaml
- run: npx -y scoria --sarif scoria.sarif

- uses: github/codeql-action/upload-sarif@v4
  with:
    sarif_file: scoria.sarif
    category: scoria
  # permissions: security-events: write が要ります
```

2つのことが起きます。実行結果ページの**ジョブサマリー**に棒グラフと表が出ます —
レビューする人がもともと見ているページです。そして各指摘が GitHub の **Security タブ**と、
**Pull Request の変更行の上**に出ます。その行を書いた人がいま見ている場所です。

## 悪化したら CI を落とす

既定では何もゲートしません。レポートを出して正常終了します。
**入れた初日に CI が真っ赤になる道具は、誰も使い続けない**からです。
baseline が落ち着いてから、設定で切り替えます。

```json
{ "mode": "ratchet" }
```

これで、どれかの観点が下がったとき、理由の書かれていない抑制が増えたとき、
`error` の指摘が新しく出たときに、実行が失敗するようになります。

**何を落とさないかも同じくらい大事です。** 次の3つは「下がったこと」は表示しますが CI は落としません。
信頼度が `low` の観点、ツールの版数が変わった観点、リポジトリの規模が大きく変わったときの
規模で割った指標。どれも「下がっていますが、ゲートはしていません」として理由付きで表示します —
**黙って除外すると、下がらなかったのと区別がつかなくなる**からです。

## 1つのリポジトリに複数のプロジェクトがあるとき

scoria が測るのは**指定された1ディレクトリだけ**で、その下には潜りません。
動かす道具がどれも「1つのルート」に紐づいているからです（`tsc` は1つの tsconfig、
`audit` は1つの lockfile）。2つのプロジェクトを含むリポジトリに向けると、
**外側だけを見ながら、両方のファイルを数える**ことになります。

なので、名前で教えてください。

```json
{ "targets": [".", "functions"] }
{ "targets": ["packages/*", "agents/*"] }
```

それぞれ「そこで scoria を動かしたのと同じ」ように測ります。
リポジトリに [`repo.json`](https://github.com/repos-json/repos-json) があれば、
その `projects` が同じ役目を果たすので、設定を書かなくても読みます。

これは架空の話ではありません。実在するプロジェクトで、リポジトリのルートに Vue アプリ、
サブディレクトリに独自の lockfile を持つ Firebase Functions、という構成のものがあります。
ルートから測ると、**型チェックは Functions の93ファイルを一度も見ずに「エラー0件」と報告し、
監査は high の脆弱性4件を見落としていました。**

## この数字が意味しないこと

**他のリポジトリと比べられません。** どの検査が動けたか、各観点が何をどう重みづけしているか、
何で割って正規化しているか — すべてリポジトリごとに違います。
こちらが72で向こうが64でも、こちらが良いという意味にはなりません。
レポートの JSON 自身が `"comparable": false` と書いていますし、バッジを使う場合も
文言に `this repo only` が入り、色は点数の高さではなく**前回からの増減**で決まります。

**較正もできていません。** すべての物差しがまだ `experimental` で、それは本当にその意味です。
49の実在リポジトリで測って「その物差しが実際に何をしているか」を調べ
（[calibration.md](calibration.md) に記録、2つは実際に直しました）、
**何をしているかは分かりましたが、正しいかどうかは分かっていません。**

なので、**推移を見て、指摘に反論して、絶対値はおおよその見取り図として扱ってください。**

## 動かないとき

### `Cannot read <パス>`

そのディレクトリが無いか、パスが違います。scoria は指定されたディレクトリから外に出ないので、
相対パスは**いまいる場所**からの相対です。

### レポートは出たが、半分が `—` になっている

これはエラーではありません。依存パッケージが install されていないので、
import をたどる検査と型チェックが対象を持てなかった状態です。`npm install` してもう一度。

### `No directory matched …`

`targets` の指定がどれにも一致しませんでした。書けるのは、そのままのディレクトリ名か、
**segment がちょうど `*`** のものだけです。`packages/*` は動きますが、
`packages/we*` や `**/src` は対応しておらず、推測せずに報告します。
**意図的に終了コード1にしています** — 0ディレクトリを測って成功と報告するのが、
誰も間違いに気づけない唯一の結末だからです。

### 検査が「skipped」と出る

飛ばした検査は必ず**probes not scored**に理由を書きます。理由はどれも地味なものです。

| 表示                                         | 対処                                                       |
| -------------------------------------------- | ---------------------------------------------------------- |
| the project's dependencies are not installed | `npm install`                                              |
| the project has no installed typescript      | install する。しないなら型エラーは未チェックのまま         |
| no lockfile to audit                         | 照合する相手がありません                                   |
| no coverage report                           | 測りたければ、先にカバレッジ付きでテストを走らせてください |
| no `.vue`, `.tsx` or `.jsx` files            | 一貫性を問う UI がありません                               |

**飛ばした検査は0点ではなく、採点から外れます。** そして「その観点を何割測れたか」が表示されます。

### `scoria.config.json` が作られた

設定の無いディレクトリでの初回実行時に、検出結果を記録するために書きます
（次回以降が同じ条件で測れるように）。試しただけなら消して構いません。
`--no-write` を付ければ最初から作りません。

### 遅い、止まっているように見える

初回の `npx scoria` はパッケージのダウンロードが入るので、20〜30秒は普通です。
以降は小さなリポジトリで1〜2秒、大きなものでも1分以内です。
それよりずっと長く止まる場合、原因はほぼ、巨大なツリーに対して動かしている外部ツールのどれかです。
`--json` でどの検査まで終わったかを見てください。各検査には2分の上限があります。

### 他のエラーで落ちた

それはバグなので、**出力を添えて教えてください。**
測定ツールが落ちるのは面倒なだけですが、事実でないことを報告するのはもっと悪いので、
どちらも聞きたいです。

## おかしいと思ったら

おかしいのかもしれません。**事実でないことを報告するのは、この道具にとって最悪の失敗**で、
実際にいくつもの誤りが「出力を読んだ人が『それは違う』と言った」ことで見つかって直っています。

誤検知だと思ったとき、あるいはコードと関係のない理由で点が動いたときは、
**そのときの出力と、リポジトリのかたち**を添えて教えてもらえると助かります。
